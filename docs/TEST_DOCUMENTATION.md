# Документация тестов

## 1. Общее описание

Проект содержит UI-автотесты для демо-приложения [the-internet.herokuapp.com](https://the-internet.herokuapp.com/), раздел **Form Authentication**.  
Тесты реализованы на Python с использованием pytest, Selenium WebDriver и паттерна Page Object Model.

Цель — проверить сценарии, описанные в тестовом задании: отображение главной страницы, переход к форме входа, авторизация с невалидными и валидными данными, выход из системы.

## 6. Предположения

1. **Выбор сайта.** В ТЗ указан `example.com` с формулировкой «любой сайт». Выбран [the-internet.herokuapp.com](https://the-internet.herokuapp.com/) как стабильный публичный стенд для UI-автоматизации с готовой формой авторизации.

2. **Ссылка «Вход».** На выбранном сайте ссылка на форму авторизации имеет текст **Form Authentication**, а не «Вход» / «Login». Семантически это тот же переход к странице логина.

3. **Редирект после успешного входа.** В ТЗ указан редирект на главную страницу. На выбранном сайте после входа пользователь попадает на **`/secure`** (Secure Area). Это считается успешной авторизацией и эквивалентом «входа в систему».

4. **Редирект после выхода.** В ТЗ указан редирект на главную страницу. На выбранном сайте после Logout пользователь возвращается на **страницу логина** (`/login`) с сообщением «You logged out of the secure area!». Это считается успешным выходом из системы.

5. **Разбиение сценария.** Помимо E2E-теста сценарий разбит на атомарные тесты для удобства локализации дефектов и параллельного запуска.

6.  **Учётные данные.** Валидный пользователь `tomsmith` — публичные тестовые credentials сайта, хранятся в `data/users.py`.

## 7. Ограничения

1. **Зависимость от внешнего ресурса.** Тесты обращаются к публичному сайту в интернете. Недоступность сайта или изменение вёрстки приведёт к падению тестов.

2. **Нет CI/CD.** Автоматический прогон в pipeline не настроен; запуск выполняется вручную или через локальную команду.

3. **Один поток.** Тесты не рассчитаны на параллельный запуск в нескольких браузерах одновременно без доработки фикстур.

4. **Мягкие проверки (`pytest-check`).** В одном тесте может выполниться несколько проверок; pytest помечает тест как failed, даже если часть assert-ов в Allure отображается как passed на этапе `call`.

5. **Flash-сообщения.** Текст уведомлений на сайте содержит символ `×`; для сравнения используется метод `get_message_text()`, который удаляет этот символ.

6. **Секреты в коде.** Пароли хранятся в репозитории как тестовые данные. Для production-проектов рекомендуется vault или переменные окружения (см. комментарий в `data/users.py`).

7. **Покрытие браузеров.** Поддерживаются Chrome и Firefox; прогон по умолчанию выполняется только в Chrome.

## 8. Page Objects

| Класс | URL | Ответственность |
|-------|-----|-----------------|
| `HomePage` | `/` | Главная страница, ссылка на авторизацию |
| `LoginPage` | `/login` | Форма входа, flash-сообщения |
| `SecureAreaPage` | `/secure` | Защищённая зона, кнопка Logout |

Общие методы (`open`, `find`, `click`, `get_message_text`) вынесены в `BasePage`.

---

## 9. Отчётность и артефакты

- **Allure:** результаты сохраняются в `allure-results/`; HTML-отчёт — через `allure serve` или `allure generate`.
- **Скриншот:** при падении теста автоматически прикрепляется к Allure-отчёту (`conftest.py`).
- **Логи:** INFO-уровень в консоли (старт/конец теста, открытие страниц, логин).
- **Отчёт о прогоне:** см. [TEST_REPORT.md](TEST_REPORT.md).
